A harness that gives coding agents short, accurate direction for one repository.

A reusable skill that inspects a repository and writes its agent harness: a root guide, an architecture map, a delivery workflow, eight working skills, and a fresh-context verifier. It writes one set of files that serves both Claude Code and Codex.

Coding agents are fast, and most of their mistakes come from missing context rather than weak reasoning. They don't know which directory owns a piece of state, which test command CI actually runs, which file is the pattern to copy, or which "obvious" refactor broke production last quarter. Long, generic prompts don't fix that. Short, accurate, repo-specific direction does.

The agentic engineering harness is a skill that writes that direction. Run it inside a repository and the agent inspects the code, the manifests, the CI configuration and any existing guidance, then writes a small set of files that tell the next agent how this particular repository works and how work here gets done.

Discovery comes before writing.

The skill starts by reading, not generating. It audits the root guides, lessons files, ADRs, lockfiles, CI, deployment config, source and test layout, and git status. It records the inspection tools an agent can use to observe the running system, the canonical file to copy for each recurring pattern, the usual test seam, and the independent source of truth for expected values. It also flags stale guidance: any command or layout a guide states that the manifests or CI contradict.

The output is deliberately small. AGENTS.md holds hard invariants as one imperative line each, the commands the repo really supports, read-only inspection tools, and "copy X for Y / do not copy Z" patterns. ARCHITECTURE.md holds current facts: a component table with a "start here" file for each, flows, contracts, trust boundaries and known unknowns. Implemented and intended are kept separate, so an agent never builds on a component that exists only in a plan.

Plans are ephemeral. Knowledge is durable.

Earlier versions of the harness kept feature ledgers and a validator script. They drifted, and agents spent effort keeping them green instead of shipping. The current design splits the two kinds of writing cleanly:

  • Plans live in .scratch/<slug>/spec.md, are gitignored, and are deleted after merge. The spec's log is the resume point when work is blocked.
  • Domain language goes in GLOSSARY.md, created only when the first term is settled.
  • Hard-to-reverse decisions go in short ADRs: one to three sentences, written only when a choice would surprise a future reader.
  • Proof of done is tests in the repository plus the evidence in the PR description.

The loop is light, and every step has a proof.

The workflow is /grill-with-docs (only when scope or a domain rule is unclear) → /to-spec → /implement, with /diagnosing-bugs as the entry point for defects. The spec step is where most of the discipline sits. Every "Done when" item carries a proof command that fails today, and "Must not change" proofs guard behavior that should survive the change. The user approves the spec before anything is built.

/implement works red-first through /tdd at the agreed seams. A missing test file or an import error does not count as red. It makes the smallest change that passes, never weakens an existing assertion, and stops after three failed repairs of the same proof, recording the root cause, the approach and what was tried. A blocked spec is a useful artifact, not a failure to hide.

A verifier that didn't write the code.

Before work is called done, /implement spawns harness-verifier in a fresh context. It can read and run commands, but it cannot edit. It checks test integrity (no weakened assertions and no tautological expected values), runs every proof, and reports findings on two separate axes. The Spec axis covers items that are missing, partial, wrong, or out of scope. The Standards axis covers bugs, security, and imports that don't exist in the manifest. Each proof is labeled Local or Live, so an offline green run is never presented as a production check.

Keeping the axes separate matters. A diff can match the spec perfectly and still leak a secret, or be clean code that quietly skips a requirement. A single blended score hides one behind the other.

One source for two agents.

The harness serves Claude Code and Codex without duplicating instructions. CLAUDE.md is a single line, @AGENTS.md. Codex reads the skills through a symlink from .agents/skills to .claude/skills, and each Codex agent file is a pointer to its Markdown definition. This is recorded as the repo's first ADR, because two copies always drift.

The skill's own repository is held to the same standard. An offline, standard-library test suite checks that documented paths exist, that every installed file has its template, that the Codex mirrors point at the Claude files, that no {{repo: …}} placeholder survives installation, that the verifier stays pinned to its model, and that every adapted skill keeps its MIT attribution. The skills are adapted from Matt Pocock's mattpocock/skills.

What it produced.

The clearest test of the harness is what it lets an agent build. I used it to build Wake, a multi-tenant team platform. Phases 1 through 5 of its proposal were specified, built test-first and verified on a single day, with each phase's spec, proofs and verifier verdict logged as it went.
