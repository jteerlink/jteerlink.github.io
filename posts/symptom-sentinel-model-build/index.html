The model factory behind Symptom Sentry’s medical image classifier.

A reproducible TensorFlow/Keras training workflow for ear and throat image classification — built to turn labeled datasets, preprocessing notebooks, and validation artifacts into deployable model assets for the Symptom Sentry app.

The Symptom Sentry app begins before a user ever opens the app. It begins in the training repository: folders of ear and throat images, notebooks that standardize preprocessing, experiments that try to separate normal from abnormal, and the quiet work of turning an experiment into an artifact the product can use.

That is why this page should not read like setup instructions. Cloning the repo is not the story. The story is the model factory behind a consumer-health image product: collect labeled examples, prepare them consistently, train a practical baseline, inspect failures, and hand the result to the application without breaking the contract between model and user experience.

GitHub Repository ↗

The application depends on a repeatable training loop.

The repository is organized around the pieces that make that loop possible: ear_dataset, throat_dataset, notebooks, and setup. That structure is simple, but it gives the work a backbone. Data domains are separated. Experiments have a place to live. Environment setup is documented. The path from image folder to model artifact is visible.

Medical-image classification is unforgiving in a way that many demo datasets are not. Consumer-captured images vary in lighting, framing, distance, sharpness, and angle. The model has to learn from examples that may not look like polished clinical inputs. Preprocessing choices become product choices because every resize, crop, normalization step, and augmentation strategy changes what the deployed model expects to see.

The training loop needs to make those choices repeatable. If the app sends an image through one path and the notebook trained on another, the product can fail in ways that are hard to diagnose. The model repository is where that contract gets defined.

EfficientNet is a practical starting point.

The project uses TensorFlow/Keras-style deep-learning workflows and an EfficientNet-oriented transfer-learning path. That is a sensible baseline for a constrained medical image task: start from an architecture that already knows useful visual representations, then adapt it to the ear and throat domains.

The point is not to make the architecture sound exotic. The point is to reduce the amount of learning the project has to do from scratch. Transfer learning lets the work focus on the dataset, preprocessing, validation, and deployment handoff instead of pretending there are enough labeled medical images to train a large model from zero.

For a portfolio case study, the strongest technical material would come from the artifacts around the model: training curves, validation curves, confusion matrices, examples the model gets wrong, and notes about what changed between runs. Those are the details that make a model build credible.

Validation is where the model earns its place in the product.

An app can show a result with confidence, but the training workflow has to explain what that confidence is worth. Accuracy alone is not enough. The project needs to know which class is harder, where false positives appear, where false negatives appear, and what kinds of images confuse the model.

In a health-adjacent context, failure review is part of the product design process. If dim throat images fail more often, the capture UI should guide lighting. If angled ear images confuse the classifier, the app should help users frame the image better. If a certain class has weaker recall, the result language should be more cautious. The training repository is where those product implications first become visible.

That connection between model behavior and product copy is easy to miss. It is also where the work becomes more than an experiment. The model does not live in a notebook forever. It shapes what the user sees, what the app asks for, and how uncertainty is communicated.

The handoff matters as much as the run.

A model artifact is only useful if the application can load it predictably. The training workflow needs versioning, conversion steps, metadata, and a clear expectation for input shape and preprocessing. Without that, every app integration becomes a guessing game.

The repository’s future-enhancement path points in the right direction: more augmentation, architecture exploration, optimization, and packaging for mobile or web inference. The next layer would make the handoff explicit. Each trained model should carry the data assumptions, preprocessing steps, evaluation summary, and version information that the app needs.

That is the quiet infrastructure behind a product like Symptom Sentry. The user sees a camera flow and a result. The app sees a model file and an API. The training repo has to preserve the chain of decisions that makes both of those things trustworthy.

What the next version should surface.

The mockup hero visual points to the right replacement for the old README-style page: datasets flow into preprocessing, preprocessing feeds transfer learning, evaluation produces review artifacts, and the final model becomes a deployable asset for the app.

The longer case study should include the exact training history once available: split strategy, augmentation choices, final metrics, confusion counts, false-positive and false-negative examples, and model-export notes. Those details would make the page feel less like a repository overview and more like a working model review.

The project is strongest when it stays grounded in that pipeline. Labeled images become a reproducible experiment. The experiment becomes a reviewed model. The reviewed model becomes an application dependency. The application dependency becomes a user-facing result that has to be clear, careful, and useful.
