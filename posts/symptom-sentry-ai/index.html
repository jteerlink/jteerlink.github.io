January 2025

A consumer-health image app designed around privacy, clarity, and auditability.

Symptom Sentry AI turns throat and ear images into structured normal-vs-abnormal assessments while keeping the product judgment explicit: guided capture, understandable confidence, secure accounts, and history users can return to.

The most delicate moment in Symptom Sentry AI is not the model prediction. It is the few seconds after a user sees the result. A person has uploaded an image of a throat or ear because something feels wrong. The software has to be useful without pretending to be a doctor, clear without being alarmist, and secure without making the experience feel heavy.

That tension shaped the project more than any individual framework choice. The application needed a modern computer-vision stack, but it also needed restraint. A health-adjacent product can lose trust by saying too much, hiding too much, or making uncertainty feel like failure. The interface, the backend, and the model bridge all had to support a simple promise: guide the user through an image analysis workflow and preserve the result responsibly.

The first decision was to narrow the answer.

It is tempting to make a medical image app feel impressive by adding categories, explanations, and dense model language. This project moves in the opposite direction. The primary output is intentionally direct: normal or abnormal, infected or not infected, with confidence and supporting context. That simplicity gives the rest of the product room to do its job.

The user journey starts with capture and upload. The UI has to make image submission feel guided rather than clinical. Once the image is analyzed, the result screen has to make the output legible: what the model saw, how confident it is, and what the user might reasonably do next. The app then gives the result continuity through history, so a user can return to past analyses instead of treating each session as disposable.

None of those pieces is flashy in isolation. Together they turn a classifier into a product flow.

The architecture follows the user journey.

The repository is organized like a full application, not a model demo. There is a frontend for interaction, a backend for APIs and authentication, TensorFlow/TensorFlow.js integration for image analysis, PostgreSQL-backed persistence, generated assets, test scripts, and documentation around the application surface.

Browser-side TensorFlow.js gives the product an important option: inference can happen close to the user when the deployment path supports it. The Node/Express backend handles the responsibilities that belong on the server: authentication, profiles, validation, API routes, session handling, and saved analysis history. PostgreSQL stores account and result context so the experience can continue across sessions.

That separation matters. Image pixels, user identity, model output, and historical records do not all have the same sensitivity or lifecycle. Treating them as separate concerns makes the system easier to reason about and safer to evolve.

Security is part of the interface.

The security features in the repo are not just backend details. HTTP-only cookies, CSRF protection, rate limiting, password hashing, input validation, and session management are part of how the app earns permission to handle sensitive interactions.

A user will never read the middleware. They will feel the result of it. Login should work cleanly. Errors should be specific enough to recover from without leaking unnecessary detail. A saved analysis should be available when expected and protected when it should be private. The interface should feel calm because the underlying system is doing its job.

The same principle applies to model feedback. A confidence score can create false certainty if it is presented like a verdict. The product language has to keep the result bounded. It can help a user notice a possible issue, organize information, and decide whether to seek care. It should not blur the line between screening support and diagnosis.

The model bridge is where the product becomes real.

Connecting JavaScript product code to TensorFlow model assets is the kind of work that decides whether a prototype becomes usable. The application supports a model bridge between frontend interaction and Python/TensorFlow-trained components, with support for multiple model variants and a binary classification path designed for a straightforward user experience.

There are many small details hidden in that bridge: file handling, preprocessing expectations, model format compatibility, response shape, error handling, and how the UI behaves while inference is running. A loading state is not cosmetic in this context. It tells the user the system is working. A graceful failure is not polish. It prevents a sensitive experience from turning into confusion.

The result history adds another layer. Saving analysis results can be valuable, but it creates responsibility. The app needs to distinguish between transient analysis and durable records. It needs authentication that is strong enough for the data it stores. It needs deletion paths and profile controls. The repository’s API surface reflects that broader product shape: register, login, logout, current user, analysis, history, save, retrieve, delete, profile, password, and subscription endpoints.

A careful product can still feel modern.

The project does not need to choose between a responsible experience and a polished one. The responsive UI, collapsible components, medical-themed loading feedback, attention-map-style result visualization, and history screens all help the product feel complete. The difference is that the polish is pointed at comprehension, not spectacle.

The best version of this page should read like a product walkthrough: a user captures an image, the app guides the upload, inference runs with clear feedback, the result is framed carefully, and the history preserves context for later. Under that walkthrough sits the technical stack: TensorFlow.js, TensorFlow, Express, PostgreSQL, secure sessions, validation, and tests.

That pairing is the value of the project. The model can classify. The application can carry the classification through a real user flow. The security layer makes the flow credible. The restraint in the product language keeps the experience honest.
